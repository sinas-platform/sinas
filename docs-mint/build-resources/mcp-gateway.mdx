The **MCP gateway** turns a [manifest](/admin/manifests) into a [Model Context Protocol](https://modelcontextprotocol.io) server. Agents and apps outside Sinas (Claude, Cursor, an in-house agent, a vibe-coded internal tool) connect to one URL and get the functions, queries and pipelines the manifest exposes, as tools, under Sinas permissions and logging.

Where [MCP servers](/build-resources/mcp-servers) let Sinas agents *consume* remote tools, the gateway lets the outside world consume Sinas resources. Together they make a Sinas instance a connector hub: central IT configures connectors, queries and pipelines once, decides who may call what, and downstream teams build on them without a copy of the credentials.

## Endpoint

```
POST   /mcp/{namespace}/{name}        # Streamable HTTP MCP server for the manifest namespace/name
```

Stateless: every request authenticates on its own with a Bearer API key, a Bearer access token or an `X-API-Key` header, so nothing is pinned to a server and nothing is replayed. Requests without a credential get `401` with a `WWW-Authenticate: Bearer` challenge; a caller without `sinas.manifests/{namespace}/{name}.read` on the manifest gets `403`.

Point an MCP client at it:

```json
{
  "mcpServers": {
    "acme-hub": {
      "url": "https://sinas.example.com/mcp/hub/agents",
      "headers": { "Authorization": "Bearer sk_..." }
    }
  }
}
```

## Exposing tools

A manifest's `exposedTools` lists what the gateway serves. Nothing is exposed unless declared:

```yaml
spec:
  manifests:
    - namespace: hub
      name: agents
      description: Tools for the engineering agents
      exposedTools:
        - { type: query, namespace: crm, name: open_orders }
        - { type: function, namespace: crm, name: refund, toolName: refund_order,
            description: "Refund an order. Asks the finance approver when above 500 EUR." }
        - { type: pipeline, namespace: ops, name: close_ticket }
```

| Field | Description |
|---|---|
| `type` | `function`, `query` or `pipeline` |
| `namespace` / `name` | The resource. It must exist, or be declared in the same config; a config that exposes a missing resource is refused. |
| `toolName` | What the agent calls it. Default `namespace__name` (unsafe characters become `_`). Names must be unique within the manifest. |
| `description` | Shown to the agent instead of the resource's own description. |

The tool's input schema is the resource's `inputSchema`; a function's or query's `outputSchema` is published as the tool's output schema and the result is returned as structured content as well as text.

A resource that is deleted or deactivated later drops out of the catalog; the manifest keeps declaring it and `/status` reports it under missing resources.

## Who sees what

The manifest selects what is on offer; the caller's own permissions decide what they get. `tools/list` returns only the exposed tools whose resource the caller may run — the same permission the tool call itself checks: `sinas.functions/{ns}/{name}.execute`, `sinas.queries/{ns}/{name}.execute`, `sinas.pipelines/{ns}/{name}.run`, by name, namespace or wildcard. A call to anything else answers "unknown tool". Two callers of the same gateway can see different catalogs.

Some resources are never served, whatever the manifest declares: inactive ones, pipelines without `asTool`, and functions with `requiresApproval` (the gateway has no one to ask, so until it supports approvals such a function is left out rather than run unapproved). `GET /manifests/{namespace}/{name}/status` reports them under missing resources.

For external agents the natural credential is a [scoped API key](/admin/users-roles#api-keys): give it the manifest's `read` permission plus the `execute` permissions of the tools that client may use, and nothing else. The key's permissions are evaluated live, so revoking or narrowing it takes effect on the next call.

Calls run exactly as an agent's tool call would: a query receives the caller's `:user_id`, `:user_email` and custom fields for row-level security, a function runs through the executor with the caller's token, a pipeline runs inline. Every call is recorded in the tool result store with `source: gateway`, the manifest, the resource and the arguments, and the HTTP request itself is in the request log with credentials redacted.

## Rate limits

Tool calls are counted per manifest and per caller (an API key is its own caller; a user token counts per user) in a fixed window. The deployment default is `GATEWAY_RATE_LIMIT_MAX_CALLS` (120) per `GATEWAY_RATE_LIMIT_WINDOW_SECONDS` (60); a manifest overrides it:

```yaml
  manifests:
    - namespace: hub
      name: agents
      gatewayLimits: { maxCalls: 600, windowSeconds: 60 }   # maxCalls: 0 disables the limit
```

Past the cap, `tools/call` answers a JSON-RPC error (code `-32029`) whose message says when to retry and whose `data.retry_after_seconds` carries the number. `tools/list` is not counted.

## Composing a tool

A tool that must read, interpret and write in one go is a [pipeline](/build-resources/pipelines) with an agent step, exposed as one tool. That keeps the sequence on the server, where the gateway can enforce it, instead of relying on the calling agent to make the calls in order.
