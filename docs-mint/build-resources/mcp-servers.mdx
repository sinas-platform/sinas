title: "MCP Servers"
description: "Remote Model Context Protocol servers as agent tool sources"
---

An **MCP server** is a remote [Model Context Protocol](https://modelcontextprotocol.io) endpoint whose tools agents can call. Register the endpoint once, enable it on an agent, and the server's tools appear in the agent's tool list — discovered live, so the server's tool list is the contract.

Supported transports: **Streamable HTTP** (recommended) and the legacy **HTTP + SSE**. Servers that only speak stdio are not supported — the backend never spawns processes for a configured resource; put such a server behind an HTTP bridge.

**Endpoints:**

```
POST   /api/v1/mcp-servers                              # Create MCP server
GET    /api/v1/mcp-servers                              # List MCP servers
GET    /api/v1/mcp-servers/{namespace}/{name}           # Get MCP server
PUT    /api/v1/mcp-servers/{namespace}/{name}           # Update MCP server
DELETE /api/v1/mcp-servers/{namespace}/{name}           # Delete MCP server
POST   /api/v1/mcp-servers/{namespace}/{name}/tools     # Connect now and list the server's tools (bypasses the cache)
```

## Configuration

```yaml
mcpServers:
  - namespace: tools
    name: tracker
    description: Issue tracker
    url: https://mcp.tracker.example.com/mcp
    transport: streamable_http            # or "sse"
    auth:
      type: bearer                        # none | bearer | header
      secret: TRACKER_TOKEN               # the *name* of a Secret, never the value
    headers:                              # optional static headers
      X-Tenant: acme
    toolAllow: ["list_*", "get_*", "create_issue"]   # glob patterns; empty = every tool
    toolDeny: ["delete_*"]                           # deny wins over allow
    timeoutSeconds: 60                    # per tool call
    connectTimeoutSeconds: 10             # connect + handshake + tools/list
```

**Auth.** The credential is a [Secret](/build-resources/secrets), resolved and decrypted in the backend at call time. Private secrets override shared for the calling user, as for connectors. `bearer` sends `Authorization: Bearer <value>`; `header` sends the value in the header you name (`header: X-Api-Key`). `secret` may be written bare (`TRACKER_TOKEN`) or in braces (`"{{TRACKER_TOKEN}}"`, as packages write it); both name the same Secret, and the bare name is stored. A configured auth whose Secret is missing refuses the call rather than sending it unauthenticated. The sandbox never sees MCP credentials.

**Tool filter.** `toolAllow` / `toolDeny` decide what the resource exposes at all; agents can narrow further per binding (below). The console's **Test & List Tools** shows the server's tools and which ones the filter hides.

## Enabling on an agent

```yaml
agents:
  - name: support
    enabledMcpServers:
      - tools/tracker                     # every tool the server allows
      - server: tools/docs
        tools: ["search_*"]               # narrowed for this agent
```

Tools are named `mcp_<namespace>__<server>__<tool>` (characters MCP allows but function names don't are replaced by `_`). The name is what the agent's `toolApprovals` rules match:

```yaml
    toolApprovals:
      rules:
        - match: "mcp_tools__tracker__create_*"
          action: ask
        - match: "mcp_*"
          action: auto
```

Status templates use the key `mcp:<namespace>/<server>/<tool>`, or `mcp:<namespace>/<server>/*` for every tool of a server (what the console's status editor offers).

**Access.** A binding grants nothing by itself: the user chatting with the agent must be able to read the server (`sinas.mcp_servers/<namespace>/<name>.read` — `:own` as its owner, `:all` otherwise), as for functions and pipelines. The API refuses a binding to a server the caller cannot read; at chat time such a server simply contributes no tools.

## How calls behave

- **Discovery degrades, never fails.** A server that is missing, inactive, unreachable or not readable by the user contributes no tools and a warning in the log; the chat turn proceeds with the other tools. Tool lists are cached in-process per server, per user and per credential for `MCP_TOOL_LIST_TTL_SECONDS` (60); a failed listing for `MCP_TOOL_LIST_FAILURE_TTL_SECONDS` (15), so a dead server isn't retried on every message. Editing a server (or rotating its secret) invalidates its cache. Error messages show the server's host and path only, never credentials a URL may carry.
- **Workbench references work.** `{"$workbench": "path"}` argument values are resolved before the call, like for every tool.
- **Results.** Text blocks are joined into `text`; `structuredContent` is passed through as `structured_content`. Images, audio and binary resources are written to the chat's workbench (`tool_results/<tool name>_<call id>_<n>.<ext>`, one set of files per call) when the agent has one, otherwise inlined as data URLs. Embedded text resources and resource links are returned as `content` entries. A tool that reports `isError` becomes an `{"error": …}` result the model can recover from. Large results spill to the workbench like any other tool result.

## Protocol version

Sinas speaks the current MCP revision, **2026-07-28**, and falls back to the older handshake-based revisions for servers that haven't moved yet. 2026-07-28 has no sessions: every request stands on its own. A server that needs state across calls (a browser, a shopping basket) returns an explicit handle from one tool, such as a `browser_id`, and the agent passes it to the next.

## Tasks

Sinas supports the [Tasks extension](https://modelcontextprotocol.io/extensions/tasks/overview) (`io.modelcontextprotocol/tasks`). A server may answer a tool call with a task instead of a result when the work takes a while:

1. Sinas polls the task inline for up to `MCP_TASK_INLINE_WAIT_SECONDS` (20), never longer than the server's `timeoutSeconds`. If it finishes in time, the agent gets the result like any other.
2. Otherwise the agent gets a `task_id` and can carry on or end its turn. Sinas keeps the task and polls it in the background at the server's suggested interval, within `MCP_TASK_MIN_POLL_SECONDS` (5) and `MCP_TASK_MAX_POLL_SECONDS` (300). The result is delivered into the chat as `[mcp task <id> completed: …]`, which wakes the agent like a finished [background job](/build-resources/system-tools).
3. When the task needs input, the request is delivered once as `[mcp task <id> needs input: …]`. The agent answers with `mcp_task_respond`, and asks the user first when the request is meant for them.

Every agent with an MCP server bound also gets three tools: `mcp_task_status` (a live look; nothing is delivered for it), `mcp_task_respond` and `mcp_task_cancel`. Cancelling is a request to the server; Sinas stops following the task either way. `list_wakeups` lists the chat's running tasks.

Tasks are kept in the database, so polling survives a restart. A task ends as failed when it outlives the server's `ttlMs` (or `MCP_TASK_MAX_AGE_SECONDS`, 7 days, when the server gives none), when the user loses access to the server, or after `MCP_TASK_MAX_POLL_FAILURES` (10) polls in a row can't reach it. Deleting the chat deletes its tasks. Polls act as the chat's user, through the API key the calling turn used, with the same credentials as the call. The agent only sees Sinas's id for a task, never the server's (which a server may use as a bearer token).

A call made outside a chat, with nowhere to deliver to, waits up to the server's `timeoutSeconds`; a task still running after that is cancelled and the call fails.

## Not supported (yet)

stdio servers; MCP resources, prompts and sampling; elicitation outside Tasks; OAuth sign-in flows for MCP servers (use a bearer token or API-key Secret). See `backend/docs/adrs/2026-10-09-mcp-client.md` and `backend/docs/adrs/2026-10-12-mcp-tasks.md`.
