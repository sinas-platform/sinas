## Prerequisites

- A VPS or server with 2+ CPU cores, 4GB+ RAM, 50GB+ storage
- A domain name pointed at the server (A record)
- An SMTP service for login emails (SendGrid, Mailgun, AWS SES, etc.) — only required if you choose `otp` or `password+otp` auth mode. Skip for `password`-only / airgapped installs.

## Install

```bash
sudo curl -fsSL https://raw.githubusercontent.com/sinas-platform/sinas/main/install.sh -o /tmp/sinas-install.sh && sudo bash /tmp/sinas-install.sh
```

The installer will:
- Install Docker if needed
- Generate secure keys (`SECRET_KEY`, `ENCRYPTION_KEY`, `DATABASE_PASSWORD`)
- Prompt for your domain, admin email, and authentication mode (and SMTP and/or admin password depending on the mode you pick)
- Create `.env` in `/opt/sinas/`
- Pull pre-built images from the container registry and start all services
- Caddy automatically provisions SSL via Let's Encrypt

All services start automatically: PostgreSQL, PgBouncer, Redis, ClickHouse, the backend API (port 8000), queue workers, the scheduler, and the web console (port 51245). Migrations run automatically on startup.

### A specific version or release candidate

By default the installer installs the latest release (`main`'s files, `:latest` images). To install a particular release or release candidate, fetch the installer from that tag and set `SINAS_VERSION`:

```bash
V=0.5.0-rc.2
sudo curl -fsSL https://raw.githubusercontent.com/sinas-platform/sinas/$V/install.sh -o /tmp/sinas-install.sh \
  && sudo SINAS_VERSION=$V bash /tmp/sinas-install.sh
```

This downloads that tag's `docker-compose.yml` and writes `IMAGE_TAG=$V` to `.env`, so files and images match. `SINAS_BRANCH=dev` installs `dev`'s files with the `:dev` images; for any other branch, also set `SINAS_IMAGE_TAG`.

The choice is saved in `.env` as `SINAS_SOURCE` (for example `version:0.5.0-rc.2` or `branch:dev`) next to `IMAGE_TAG`. A later run without `SINAS_VERSION`, `SINAS_BRANCH` or `SINAS_IMAGE_TAG` reuses it and says so, so an update keeps files and images together. Running it with another `SINAS_VERSION` or `SINAS_BRANCH` moves the install there. The update command printed at the end of an install repeats the settings it used.

### Non-interactive install

For CI, provisioning scripts or agents, set `SINAS_NONINTERACTIVE=1` and pass the answers as environment variables instead of answering prompts:

| Variable | Required | Description |
|---|---|---|
| `SINAS_DOMAIN` | yes | Domain name |
| `SINAS_ACME_EMAIL` | yes | Email for SSL certificates |
| `SINAS_SUPERADMIN_EMAIL` | no | Superadmin email (default: `SINAS_ACME_EMAIL`) |
| `SINAS_AUTH_MODE` | no | `otp` (default), `password` or `password+otp` |
| `SINAS_SUPERADMIN_PASSWORD` | no | Password modes only, at least 8 characters. Empty: a one-time setup link is printed at the end |
| `SINAS_SMTP_HOST`, `SINAS_SMTP_USER`, `SINAS_SMTP_PASSWORD` | with `otp` or `password+otp` | SMTP server for login codes |
| `SINAS_SMTP_PORT`, `SINAS_SMTP_DOMAIN` | no | SMTP port (default `587`) and from-domain |
| `SINAS_CONFIGURE_FIREWALL` | no | `y` to configure UFW on Linux (default `n`) |
| `SINAS_START` | no | `n` to write the configuration without starting Sinas (default `y`) |

```bash
sudo SINAS_NONINTERACTIVE=1 SINAS_VERSION=0.5.0-rc.2 \
  SINAS_DOMAIN=sinas.example.com SINAS_ACME_EMAIL=ops@example.com SINAS_AUTH_MODE=password \
  bash /tmp/sinas-install.sh
```

A missing or invalid answer stops the installer with an error before `.env` is written. An existing `.env` is kept, as in interactive runs. The setup link is printed on a line of its own under step 4 of the summary. The installer exits non-zero when the install did not finish: Sinas was to start and the backend is not running, or a password-mode superadmin got no setup link (the backend did not become ready, or it is a version before 0.5.0 without the setup-link command). It says where to look in each case. `SINAS_START=n` (configuration only) exits zero.

## Update

```bash
cd /opt/sinas
docker compose pull
docker compose up -d
```

The backend applies database migrations on startup. Each migration commits on its own, so a table is locked only for that migration's brief schema change, not for the whole upgrade.

### Upgrading to 0.5.0

0.5.0 marks every existing provider batch-API usage row (`source: provider_batch`) as `batch: true`. On an install with many of them this rewrites most of `llm_usage` and leaves dead rows behind. The migration does this in short batches while Sinas keeps serving. Once the upgrade is done, clean up the dead rows and refresh the planner statistics:

```bash
docker compose exec postgres psql -U postgres -d sinas -c "VACUUM (ANALYZE) llm_usage;"
```

Use your own database user and name if you changed `DATABASE_USER` or `DATABASE_NAME`; on Kubernetes or an external database, run the same statement with your usual client. Autovacuum would get there eventually, but running it yourself keeps usage queries fast straight away. It takes no locks that block reads or writes.

0.5.0 runs the bundled Redis with `maxmemory-policy noeviction` instead of `allkeys-lru` (Compose and the Helm chart, including the lite profiles). Redis holds Sinas' queues, locks, stream relays and dead-letter queue, not a cache: under memory pressure `allkeys-lru` could silently drop queued jobs or locks. With `noeviction`, a Redis that reaches `maxmemory` (`REDIS_MAXMEMORY`, 256mb; 128mb for the lite profile) evicts nothing and refuses writes instead. While it is full, anything that has to write fails, visibly: API requests answer 503 with `"code": "redis_out_of_memory"`, new jobs wait in the queue, jobs and agent turns already running usually fail, and the workers keep running and log that Redis is full. The System page shows Redis memory and warns from 75% of `maxmemory`. See [When Redis is full](/getting-started/kubernetes#when-redis-is-full). Everything Sinas writes to Redis now expires or is bounded, so a normal install stays far below the limit. To keep the old behaviour, set `REDIS_MAXMEMORY_POLICY=allkeys-lru` in `.env` (Helm: `redis.maxmemoryPolicy`).

**Before upgrading, check Redis memory.** A busy install under `allkeys-lru` can sit at `maxmemory`; switched to `noeviction` with its data kept (the new policy applies when `docker compose up -d` recreates the Redis container), it would be full from the first write:

```bash
docker compose exec redis redis-cli INFO memory | grep -E 'used_memory:|maxmemory:'
docker compose exec redis redis-cli INFO stats | grep evicted_keys
```

If `used_memory` is near `maxmemory`, or `evicted_keys` is above 0, raise `REDIS_MAXMEMORY` in `.env` (Helm: `redis.maxmemory`) in the same upgrade. Workers and the scheduler also log an error at startup when Redis is at 90% of `maxmemory` or more.

0.5.0's `docker-compose.yml` also adds a `proxy` network between Caddy, the backend and the console, with the fixed subnet `10.254.253.0/24` (see [Client IPs](#client-ips-behind-caddy) below). `docker compose up -d` creates it. If that subnet is already in use on your host or network, set `SINAS_PROXY_SUBNET`, `SINAS_PROXY_IP_RANGE`, `SINAS_CADDY_IP` and `FORWARDED_ALLOW_IPS` in `.env` first.

## Client IPs behind Caddy

Login and OTP rate limits count requests per client IP, and request logs record it. Caddy replaces any `X-Forwarded-For` a client sends with the address it sees, and the backend believes that header only on connections from Caddy: Caddy is the only container on the `proxy` network with a fixed address (`SINAS_CADDY_IP`), and `FORWARDED_ALLOW_IPS` trusts that one address. A client that reaches port 8000 directly is counted by its own address, whatever header it sends.

To put another proxy in front instead of Caddy, set `FORWARDED_ALLOW_IPS` to its address as the backend container sees it. See [Client IP behind a reverse proxy](/getting-started/environment-variables#client-ip-behind-a-reverse-proxy).

## Log in

1. Open the console at `https://yourdomain.com:51245/ui/`
2. Enter your `SUPERADMIN_EMAIL` address
3. Then, depending on your `AUTH_MODE`:
   - `otp` — check your inbox for the 6-digit code
   - `password` — enter your password (see [First admin access](#first-admin-access-with-a-setup-link) if you don't have one yet)
   - `password+otp` — enter your password, then the emailed code
4. You're in. See [Authentication](/platform/authentication) for the full reference.

## First admin access with a setup link

With a password mode and no `SUPERADMIN_PASSWORD` (what the installer does when you leave the password empty), the superadmin starts without a password and chooses one through a one-time **setup link**: `https://yourdomain.com:51245/ui?token=…`.

The installer prints the link once at the end of a fresh install. To get one yourself (the link is never written to the logs; the backend logs only this command):

```bash
# docker compose (run in /opt/sinas)
docker compose exec backend python -m app.cli setup-link

# all-in-one compose profile
docker compose -f docker-compose.lite.yml exec sinas python -m app.cli setup-link

# Kubernetes (Helm)
kubectl exec -n sinas deploy/backend -c backend -- python -m app.cli setup-link
```

It defaults to `SUPERADMIN_EMAIL`; `--email someone@example.com` mints one for any active user. The URL goes to stdout on its own line, so a script can capture it.

Opening the link spends it and shows **Set your password**; saving signs you in and lands on the dashboard (with `password+otp`, the emailed code is asked first). Expiry and reuse:

- A link is valid for 24 hours (`PASSWORD_RESET_TOKEN_TTL_HOURS`) and works **once**. After it is opened there are 30 minutes to save the password.
- Minting a new link for a user invalidates the previous one, and so does setting the password.
- A used, expired or replaced link shows "This link is invalid or has expired" with a way to the login page; run the command again for a fresh one.

See [Setup links](/platform/authentication#setup-links) for the details.

## Configure an LLM provider

Before agents can work, you need at least one LLM provider:

```bash
curl -X POST https://yourdomain.com/api/v1/llm-providers \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "openai",
    "provider_type": "openai",
    "api_key": "sk-...",
    "default_model": "gpt-4o",
    "is_default": true
  }'
```

## Start chatting

A default agent is created on startup. Create a chat and send a message:

```bash
# Create a chat with the default agent
curl -X POST https://yourdomain.com/agents/default/default/chats \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{}'

# Send a message (use the chat_id from the response)
curl -X POST https://yourdomain.com/chats/{chat_id}/messages/stream \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"content": "Hello!"}'
```
